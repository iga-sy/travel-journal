# 旅行フォルダの取り込み

ユーザーはこのプロジェクト直下（`旅行記録/`）に、旅行タイトルが分かるフォルダ名で新しいフォルダを作り、写真を保存していく運用。そのフォルダを検出したら、以下の手順でサイトのデータに変換する。JSONを直接書かせることはしない（[[travel_journal_data_workflow]]memory参照）。

## 手順

### 1. フォルダの特定と写真の棚卸し
- 対象フォルダをユーザーに確認（フォルダ名が旅行名のヒントになることが多い）
- フォルダ直下の写真＝**アルバム用の一般写真**
- サブフォルダ「スケジュール用」があれば、そこに入っている写真＝**スケジュール項目に紐付ける写真**（このサブフォルダ運用は本人の指定した方式）
- **拡張子だけでは判断しない**：`.HEIC`でも中身が実際はJPEG（マジックバイト`ffd8ff`）ということがある。Node scriptでバッファの先頭バイトを見て判定する

### 2. Exif抽出とJST変換
- `exifr`（devDependencies済み）で`DateTimeOriginal`を取得
- **注意**：このユーザーの環境ではExifの生時刻をUTCとして解釈すると、+9時間した値が実際の店の営業時間と整合した（＝日本時間として扱うには+9h補正が必要だった）。新しい写真セットでも、抽出した時刻が明らかに不自然（深夜に営業してるはずの店など）なら+9h補正を試す。逆に既に自然な時刻ならそのまま使う
- Exifが無い写真（メッセージアプリ経由などで失われることがある）は、ファイル番号（`IMG_XXXX`）の前後関係から日付を推定する

### 3. HEIC→JPEG変換
- `heic-convert`（devDependencies済み）を使用。中身が実際はJPEGだったファイルはそのままコピー（手順1の判定を利用）
- 出力先は`assets-source/photos/<tripId>/`（`public/photos/`ではない。ここが暗号化前の原本置き場）
- ファイル名は`day{N}-general-{NN}.jpg`（一般写真）／`day{N}-{NN}-{slug}.jpg`（スケジュール写真、店名などのスラッグ付き）のように分かりやすく

### 4. スケジュール項目の推定とユーザー確認
- 「スケジュール用」写真はReadツールで実際に開いて内容を目視し、店名・場所を推測する
- 看板やレシートが写っていて店名を直接読み取れることも多いが、読み取れない写真も普通にある（那須2025-2026では7枚中3枚が読み取れず）。その場合は無理に決め打ちせず、ユーザーに自由記述で聞く
- **質問文を書く際は写真ごとに完全に独立させる**：他の写真で読み取れた看板テキスト（営業時間・店名など）をうっかり別の質問に書き込むと、ユーザーがその情報から店を誤認して回答してしまう（実際に那須2025-2026で発生：ある店の「open10-17・金曜定休」という営業時間を別の未確認の写真の説明に混入させてしまい、ユーザーの回答が意図と違う店を指してしまった）。各写真の特徴（建物の外観・料理内容・時刻）だけを正確に書き、他の写真の情報を混ぜない
- ユーザーは複数写真分の店名をまとめて改行区切りで一括回答することが多い。回答順は質問を並べた順と対応している前提で読み、対応が怪しい場合は遠慮せず再確認する
- 時刻の丸め方（例：「30分刻みで」等）を指定されたら、全スケジュール項目に機械的に適用する。一部だけ丸めて他を生の時刻のまま残す取りこぼしをしないよう、確定後に一覧で見直す

### 5. 住所・座標の取得
- 店名が確定したらWebSearchで住所を検索
- 座標のジオコーディングは以下を使い分け：
  - 番地までの日本の住所 → 国土地理院API `https://msearch.gsi.go.jp/address-search/AddressSearch?q=<住所>`
  - 山・観光地などの地物名 → Nominatim `https://nominatim.openstreetmap.org/search?q=<地物名>&format=json`（`User-Agent`ヘッダ必須）
- **重要**：このWindows環境はシステムコードページがShift-JIS(932)のため、Bash経由の`curl --data-urlencode`に日本語を渡すと文字化けする（[[windows_curl_encoding_gotcha]]memory参照）。**必ずNode.jsの使い捨てスクリプトで`fetch`を使うこと**。curlに日本語引数を直接渡さない
- Googleマップリンクは座標ではなく`https://www.google.com/maps/search/?api=1&query=<店名+住所>`形式のテキスト検索URLにする（座標精度が粗くても正しい場所に飛べる）

### 6. データ組み立て
`src/types/trip.ts`のスキーマに従う：
- `schedule[]`：date/time/name/category（食事・カフェ・観光・移動・宿泊のいずれか。カフェ的な店は「カフェ」に）/address/location/googleMapsUrl/officialUrl/instagramUrl/memo/photos
- トップレベル`photos[]`：スケジュールに紐付かない一般アルバム写真（path/date/time）
- `coverPhoto`：象徴的な1枚を選ぶ（後でユーザーがサイト上のEditモードから変更可能）
- `comments`は空配列`[]`にしておく（サイト上でユーザーが追記する用）

`src/data/trips/<tripId>.json`を新規作成し、`src/data/trips-index.json`にサマリ（id/name/startDate/endDate/regions/coverPhoto/photoCount/comment/location）を追記する。

### 7. 反映・確認
- `node scripts/encrypt-data.mjs`を実行（`.env.local`の`SITE_PASSWORD`が必要）
- `npm run dev`でVite開発サーバーを起動し、ブラウザで実際に開いて確認（トップページのカード・詳細ページの旅程/アルバム/地図）。具体的な起動・パスワード突破・スクリーンショット手順は`run-travel-journal`スキルを使う
- 確認後、取り込み元の生フォルダ（プロジェクト直下の元フォルダ）は削除してよいかユーザーに確認してから片付ける（変換済みは`assets-source/photos/`に残るので原本は不要になることが多い）
